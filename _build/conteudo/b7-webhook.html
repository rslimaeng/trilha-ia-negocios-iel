01
O que você vai aprender

Por que isso importa

Em uma frase

Com Webhook, qualquer sistema que saiba mandar uma requisição HTTP (ou seja: todos) consegue disparar seu workflow. É o trigger que abre o n8n pro mundo.

Webhook é a porta de entrada universal do n8n. Sem ele, você fica preso aos integradores nativos: quando aparece uma ferramenta que o n8n não tem nó, você não consegue receber nada dela.

02
O conceito, e é um só

Conceito central

O conceito desta aula

Webhook Trigger = o n8n te dá uma URL única. Tudo que chegar nessa URL via HTTP (POST, GET, etc.) dispara o workflow

  • Entrada: uma chamada HTTP de fora (qualquer sistema)
  • Saída: 1 item com headers, body, query, params da requisição
  • Quando dispara: quando alguém bate naquela URL
  • Pré-requisito crítico: workflow precisa estar ativado pra usar URL de produção
Analogia

Webhook é o vizinho fofoqueiro: fica esperando, e quando algo acontece lá fora, te avisa na hora. Diferente do HTTP Request (que vai BUSCAR fora), Webhook espera ser chamado.

  • O vizinho de plantão = a URL do Webhook, esperando
  • Algo acontece lá fora = outro sistema faz a chamada HTTP
  • Te avisa na hora = o workflow dispara com o que chegou

Em sala a analogia foi a campainha; no Notion, o vizinho fofoqueiro. É a mesma ideia: o n8n espera, alguém de fora toca.

03
Como funciona

Como funciona na prática

As 2 URLs (a pegadinha mais comum)

Toda vez que você adiciona um Webhook Trigger, o n8n gera 2 URLs diferentes:

URLQuando usarPré-requisito
Test URLPra desenvolver/testarClicar em Listen for Test Event primeiro
Production URLPra usar em produçãoWorkflow precisa estar ativado

A Test URL só funciona enquanto o n8n está "escutando" (botão "Listen for test event" pressionado). Ela expira sozinha após 1 chamada ou se você fechar o painel.

A Production URL funciona pra sempre: desde que o workflow esteja ativo.

As duas portas, como foram mostradas em sala. A tabela acima é este slide em texto; a pegadinha 1 da cerca é misturar as duas.

Métodos HTTP

Webhook aceita escolher o método. Os 2 mais comuns:

  • GET: quando o sistema externo só passa dados na URL (?nome=Ana&idade=30).
  • POST: quando o sistema externo manda dados no corpo da requisição (formato JSON, geralmente).
Padrão pra começar: POST

A maioria das integrações modernas (formulários, plataformas de pagamento, etc.) manda POST com JSON.

Como testar (3 jeitos)

  1. Abrir a URL no navegador: funciona pra GET, mostra resposta na tela.
  2. Postman ou Insomnia: ferramentas gratuitas pra mandar POST/PUT/DELETE com payload customizado.
  3. Outro sistema chamando de verdade: Typeform, ManyChat, etc. Configura a URL como webhook deles.

A demonstração

Exemplo guiado: Webhook que recebe e mostra o que chegou

Exemplo guiado · Webhook Hello
  1. Crie workflow novo. Renomeie pra Webhook Hello.
  2. Adicione Webhook → renomeie pra 📡 Webhook Receber.
  3. Configure: HTTP Method POST; Path: deixa o default (vai gerar URL única).
  4. Copie a Test URL (botão de cópia ao lado).
  5. Clique em Listen for Test Event (botão laranja embaixo).
  6. Em outra aba, abra o Postman (ou use curl no terminal):
A requisição de teste · POST com JSON 
POST https://[sua-url]/webhook-test/[id-único]
Body (JSON):
{ "nome": "(seu nome)", "curso": "n8n" }
  1. Mande a requisição. Volta no n8n: você vê o item chegando.
  2. Olhe o Output do Webhook: tem headers, body (com nome e curso), query, params.

Redesenho do canvas, a partir da execução de teste (execução 417, 16/09/2026). O que o Webhook entregou, na visão JSON:

Output do 📡 Webhook Receber 
{
  "headers": { "content-type": "application/json" },
  "query": {},
  "body": { "nome": "(seu nome)", "curso": "n8n" }
}

Repare onde os seus dados chegaram: dentro de body, não na raiz. É por isso que, no próximo nó, o nome se lê como {{ $json.body.nome }}. O teste de 16/09 foi feito com a chamada de teste do próprio n8n, sem Postman; o formato do item é o mesmo de uma chamada real.

Pronto. Você criou um endpoint que qualquer sistema do mundo pode chamar.

05
A cerca

Pegadinhas

Misturar Test URL e Production URL

Você desenvolve com Test, configura no sistema externo a Test, esquece de trocar pra Production quando ativa. Resultado: produção quebrada. Sempre troque pra Production URL antes de ativar.

Esquecer de ativar o workflow

Production URL só funciona com workflow Active = ON. Test URL ignora ativação (só pede "Listen for Test Event").

Não validar formato do body

O sistema externo pode mandar JSON, form-urlencoded, multipart. Cada um chega num formato diferente em $json.body. Sempre inspecione o output do Webhook antes de assumir formato.

Usar GET quando precisa enviar dados sensíveis

GET expõe dados na URL (que ficam em logs). Pra dado sensível, sempre POST com body.

Não autenticar webhook em produção

A URL é "secreta" mas vaza fácil (logs, prints, screenshare). Pra produção real, use Basic Auth ou Header Auth nas opções do Webhook (B9 destrincha mais).
