Conceito central

O conceito desta aula

O ciclo padrão do Webhook Trigger

Por padrão, quando você cria um Webhook Trigger e ele recebe uma chamada, o n8n responde 200 OK automaticamente: sem dado, só pra confirmar que recebeu. Suficiente em 70% dos casos (formulário capturado, evento registrado).

Mas em 30% dos casos, quem chamou o webhook precisa receber dado de volta:

  • Chatbot ManyChat espera o texto da resposta pra mostrar pro usuário.
  • Site espera os dados enriquecidos pra renderizar a tela.
  • Sistema externo espera confirmação estruturada (tipo status: approved, id: 42).

Solução: mudar o modo Respond do Webhook Trigger e adicionar o nó Respond to Webhook no fim do fluxo.

Os três degraus, em slide. O slide usa o nome do instrutor como dado de exemplo ({ nome: Rafael } entra, { saudacao: Ola Rafael } sai); na aula, o exemplo usa (seu nome), e no teste usou "Ana". A pegadinha do quadro é a primeira da cerca.

Os 3 modos de Respond do Webhook Trigger

ModoQuando usar
Immediately (default)Confirma na hora com 200 OK vazio. Workflow continua em background. Use quando o chamador não precisa esperar.
When Last Node FinishesEspera o workflow inteiro rodar e devolve o output do último nó. Útil quando o último nó já é o que você quer devolver.
Using Respond to Webhook NodeVocê decide exatamente onde, como e o que responder. Adicione o nó Respond to Webhook no ponto certo do fluxo. Modo mais usado em mini-API séria.

Tabela remontada: três modos que o export tinha espremido em duas linhas. Conferido na tela em 16/09/2026: no nó, o campo se chama Respond e a terceira opção aparece como "Using 'Respond to Webhook' Node".

Como funciona na prática

Setup mínimo do modo "Using Respond to Webhook Node"

O setup mínimo, em 3 partes 
1. Webhook Trigger:
   - Path: minha-api
   - Method: POST
   - Respond: Using Respond to Webhook Node

2. (nós do meio: HTTP Request, Set, IF, AI Agent, etc.)

3. Respond to Webhook node (ultimo da branch):
   - Respond With: JSON
   - Body: { saudacao: Ola NOME }

Atalho: o Respond to Webhook aceita JSON, Text, HTML, Binary e No Body. JSON é o mais comum.

Onde colocar o nó Respond to Webhook

Regra: ele tem que ser o último nó da branch que processa o pedido. Se você ramifica com IF, cada branch precisa do seu próprio Respond (ou converge antes do Respond único).

Um Respond por branch 
[Webhook Trigger]
        |
   [Validacao]
        |
       IF -- valido?
       /        \
   true          false
     |             |
[Processa]    [Respond: erro]
     |
[Respond: sucesso]
04
A demonstração

Exemplo guiado: sua primeira mini-API em 10 minutos

Exemplo guiado · recebe um nome, devolve uma saudação

Webhook que recebe { nome: (seu nome) } e devolve { saudacao: Ola (seu nome), bem-vindo! }. Mini-API completa.

1. Webhook Trigger

  • Adiciona um Webhook Trigger. Renomeia: 🎣 Recebe Pedido.
  • HTTP Method: POST
  • Path: saudacao
  • Respond: Using Respond to Webhook Node (importante!)
  • Clica em "Listen for Test Event". n8n abre uma URL de teste: copia ela.

2. Set (Edit Fields): monta a saudação

  • Adiciona um Edit Fields. Renomeia: 📝 Monta Saudacao.
  • Adiciona campo:
    • Nome: saudacao
    • Valor: arrasta body.nome do painel esquerdo. Vira a expression que monta Ola {{ $json.body.nome }}, bem-vindo!
Pegadinha numero 1

O dado que vem pelo POST aparece dentro de body: $json.body.nome, não $json.nome.

3. Respond to Webhook

  • Adiciona o Respond to Webhook. Renomeia: 📤 Devolve Resposta.
  • Respond With: JSON
  • Body: monta um JSON com a chave saudacao referenciando {{ $json.saudacao }}.

4. Testa

Em outro app (Postman, Insomnia, ou um cliente HTTP do seu navegador), faz um POST pra URL de teste com body { nome: (seu nome) }. Resposta:

A resposta da mini-API 
{ saudacao: Ola (seu nome), bem-vindo! }

Você acabou de virar fornecedor de API. Qualquer sistema do mundo pode chamar essa URL e receber resposta personalizada. ManyChat, Wix, formulário, app móvel: todos funcionam com esse padrão.

Redesenho do canvas, a partir da execução de teste (execução 450, 16/09/2026). O pedido de teste entrou com { "nome": "Ana" } no body, o Set montou { "saudacao": "Ola Ana, bem-vindo!" } e o Respond devolveu o mesmo JSON. Duas coisas a declarar: o POST de teste foi feito pela ferramenta que executa o workflow (ela pina o pedido no nó Webhook), não por um Postman; e o painel do nó, conferido na tela, mostra as duas URLs lado a lado, "Test URL" (/webhook-test/saudacao) e "Production URL" (/webhook/saudacao), com o botão "Listen for test event" no canto superior direito.

05
A cerca

Pegadinhas

Esquecer de mudar o Respond pra "Using Respond to Webhook Node"

Sem isso, o Webhook Trigger responde 200 OK vazio na hora e ignora o nó Respond no fim.

Respond to Webhook não é o último nó da branch

Tudo que vem depois dele não roda: porque a resposta já foi.

Test URL vs Production URL

O Webhook Trigger tem 2 URLs distintas: a Test URL (/webhook-test/...) só funciona com o n8n em modo "Listen". A Production URL (/webhook/...) funciona depois que você ativa o workflow. Aluno testa com Production URL e fica frustrado.

Dado vem dentro de body

$json.body.nome, não $json.nome. Sempre confere o JSON view.

Timeout de 30s

A maioria dos chamadores (browsers, ManyChat, Stripe) desiste em ~30s. Workflow que demora muito (chamada pra OpenAI lenta + 5 nós) pode estourar o tempo do chamador. Pra processos longos, retorne Immediately e processe em background.

CORS em integração com browser

Se o webhook é chamado por código JavaScript de um site, o browser pode bloquear por CORS. Solução: setar header Access-Control-Allow-Origin no Respond to Webhook (campo Headers).
